# LLaMer

Конфигурируемый движок агентного ревью диффа. Собирает изменения задачи, прогоняет их
через этапы на моделях (`claude` или `codex`) и отдаёт результат либо в GitLab — тредами
на строках, либо агенту, который его запустил, — отчётом и JSON.

Знания о конкретном проекте в движке нет. Встроенные этапы со своими заданиями и скиллами идут без
настройки; свои этапы, скиллы сверх встроенных, разрешённые команды, драйверы, уровни и
трекер задаёт `.llamer.json` в корне проекта.

## Установка

```bash
npm i -g github:hakastein/llamer#v0.3.0
llamer --help
```

Нужен Node ≥ 24 и git ≥ 2.38 (`git merge-tree --write-tree`). Зависимостей у пакета нет. Драйвер (`claude` или `codex`), его
вход, скиллы этапов и всё, что нужно этим скиллам (навигация по коду, docker и прочее),
готовит тот, кто запускает.

## Запуск

Вход — ровно один:

| Флаг | Что разбирается |
|---|---|
| `--mr <url\|project!iid>` | merge request в GitLab. Для `project!iid` адрес GitLab берётся из `GITLAB_URL` (или `CI_SERVER_URL`) |
| `--local [--target <ветка>]` | рабочее дерево вместе с незакоммиченным и неотслеживаемым против целевой ветки. Без `--target` — ветка `origin/HEAD`, без неё — `main` |
| `--base <sha> --head <sha>` | две ревизии репозитория; сравнение — от `--base` как есть |

Выход:

| Флаг | Что получается |
|---|---|
| по умолчанию | отчёт: `report.md` в каталоге прогона и JSON находок в stdout |
| `--publish gitlab` | заметка о рисках, закрытие снятых тредов, треды находок на строках, сводка и статус в MR. Только с `--mr` |
| `--dry-run` | ничего не публиковать: вместо `--publish` — отчёт |

Прочее: `--config <файл>` — конфиг вместо `.llamer.json` в корне репозитория,
`--preflight` — проверить окружение и напечатать JSON пробелов, не начиная прогон.

`--since-last` (только с `--mr`) — повторный прогон по тому же MR разбирает только
изменения после прошлого прогона LLaMer. Прошлый прогон — метка `llamer-rev` в
заметке-статусе, которую оставляет `--publish gitlab`; берётся последняя метка, чья
ревизия есть в истории головы MR. Метки вне истории (force-push, rebase) пропускаются с
записью в лог. Ревизия метки становится ещё одной базой изменений задачи: уже разобранное
отсеивается так же, как код целевой и общих веток. Нет годной метки или она совпала с
базой MR — разбирается весь реквест. Новых изменений после метки нет — этапы не
поднимаются; с `--publish gitlab` в MR ничего не пишется (статус прошлого прогона
остаётся в силе), только строка в логе, а отчёт выходит с пустыми находками.
Сорвался этап, этап прекратил работу командой `stop` или не опубликовалась находка — статус выходит без метки, и следующий
`--since-last` считает от прошлой полной метки (нет её — весь реквест).

```bash
llamer --local --preflight          # готово ли окружение
llamer --local                      # отчёт по своей ветке
llamer --mr https://gitlab.example.com/group/project/-/merge_requests/123 --publish gitlab
```

Весь лог идёт в stderr; stdout несёт только JSON — отчёт (см. «Отчёт») или, с
`--preflight`, пробелы окружения; при `--publish gitlab` он пуст. Код возврата 0 — прогон
дошёл до результата, 1 — нет. Ошибка конфига, входа или пробел preflight останавливают
прогон до начала: stdout пуст, код 1, причина — в stderr. Сорвавшийся прогон отдаёт JSON
с `"ok": false` и код 1.

Если голова разбора (`--mr`, `--head`) не совпадает с `HEAD` рабочей копии, она
выкладывается отдельным `git worktree` во временный каталог и убирается после прогона:
рабочее дерево не трогается.

## Протокол прогона

Протокол зашит в движок:

1. **Оценка** — служебный этап `assess` выносит природу правки, риск и уровень глубины
   разбора (1–5). Без его вердикта прогон останавливается: неизвестно, на какой глубине
   разбирать. При GitLab-входе в той же волне идёт этап **тредов** (`threads`): сверяет
   наши открытые треды прошлых прогонов с текущим кодом и закрывает снятые.
2. **Волна разбирающих этапов** — встроенные `logic` (бизнес-логика) и `quality`
   (качество кода) и свои этапы из `stages` конфига, параллельно. Этап на нескольких
   драйверах идёт экземпляром на каждый драйвер; экземпляры называются `<этап>·<драйвер>`
   (`logic·claude`, `logic·codex`) в логе, таблице цены, отчёте и журнале, задание у них
   общее. Экземпляры независимы: в `list` и `amend` экземпляр не видит находок других
   экземпляров своего этапа, сводит их дедупликация. Этап с масками `paths` поднимается,
   только если в изменениях есть файлы под них.
3. **Дедупликация** (`dedupe`) — помечает находки разных этапов и экземпляров про одно место и одну
   причину; помеченные не публикуются и до скептика не доходят.
4. **Скептик** (`skeptic`) — вердикт по каждой уцелевшей находке, вес в обе стороны.
5. **Публикация** — в GitLab или отчётом.

В каждой волне первым стартует ведущий этап, остальные — когда модель начала ему
отвечать: общая часть пакета (дифф и треды) у всех этапов одна байт в байт и ложится в кэш
промпта один раз.

### Что разбирается: изменения задачи

Этапы разбирают не дифф реквеста, а **изменения задачи** — то, что голова добавляет к
целевой ветке и к общим веткам из `sharedBranches`. База — слияние merge-base головы с
каждой из этих веток (`git merge-tree`), записанное коммитом; чужой код, пришедший в ветку
из общих веток, в разбор не попадает. Конфликтный между общими ветками файл берётся по
диффу реквеста. При `--mr` ветки догружаются из `origin` (неглубокий клон — только
коммитами). Треды встают на строки диффа реквеста: находка на строке, которой в нём нет,
уезжает заметкой без привязки.

Изменений своих нет — этапы не поднимаются, выходит отчёт или статус «своих изменений нет».
Изменения задачи не вычислились — ревью не идёт вовсе.

### Как этапы пишут находки

Этап не пишет в GitLab сам: он вызывает `review` — команду, которую движок кладёт
в `PATH` этапа. Харнесс проверяет каждую запись (находка — только на изменённой строке
изменений задачи, правка кнопкой — применима) и пишет журнал прогона; публикует движок.
Команды у каждого этапа свои, чужую харнесс отбивает:

| Этап | Команды |
|---|---|
| разбирающий | `finding`, `amend`, `batch`, `list`, `blame`, `summary`, `stop` |
| `assess` | `assess`, `stop` |
| `threads` | `resolve`, `thread`, `list`, `batch`, `blame`, `stop` |
| `dedupe` | `dupe`, `list`, `batch`, `blame`, `stop` |
| `skeptic` | `verdict`, `list`, `blame`, `batch`, `stop` |

В задании этапа справки команд нет — одна строка, что команды и форматы в `review --help`:
он печатает перечень команд этапа и справку каждой; справка одной команды — `review <команда> --help`.
Протокол находок, команды харнесса и встроенные этапы со своими скиллами (`skills/`
пакета) движок везёт сам; остальные методы этапов приходят скиллами из `skillPaths`.

Токены GitLab и трекера читает движок, а не этапы. Окружение этапа — белый список:
`PATH`, `HOME`, `LANG`, `LC_*`, `TZ`, `TMPDIR`, `USER`, `SHELL`, `TERM`, прокси
`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY` (в обоих регистрах), сертификаты
`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, переменные входа своего драйвера
(см. «Драйверы»), служебные переменные харнесса и `drivers.<имя>.env` конфига. Токены GitLab
и трекера, `CI_*` и всё прочее в этап не попадают — адрес API и подобное драйверу задаются
в `drivers.<имя>.env`. Значения секретов, которые держит
движок (переменные `*_TOKEN`, `*_KEY`, `*_SECRET`, `*_PASSWORD`), вымарываются из всего,
что уходит в GitLab, в `report.md`, JSON отчёта, журналы этапов, журналы сессий и лог движка в stderr.

## Конфиг `.llamer.json`

Незнакомая версия и любой неизвестный ключ на любом уровне останавливают прогон.

Конфиг и `.claude/` разбираемого дерева исполняются как код — бинарь драйвера, команды
`allow`, настройки claude: движок доверяет дереву ровно как CI, который его запускает.

| Ключ | Что задаёт | По умолчанию |
|---|---|---|
| `version` | версия схемы, сейчас `1` | обязателен |
| `skillPaths` | каталоги скиллов: скилл — подкаталог с `SKILL.md`. Путь — от каталога конфига, `~` и `${VAR}` раскрываются. Одноимённые скиллы в разных каталогах — ошибка; одноимённый со встроенным скилл ошибкой не считается, этап получает встроенный | `[]` |
| `allow` | команды, разрешённые всем этапам, — префиксы из слов без метасимволов оболочки (`"rg"`, `"git log"`). Команды харнесса разрешены всегда | `[]` |
| `prompt` | строки задания, которые знает проект: `protocol` дописывается в раздел «How This Run Works» после строк о поиске, `plan` заменяет план по умолчанию в «Your Plan» (поиск по тексту). Так проект говорит этапам о навигации, которую сам поднял и разрешил в `allow`, — пример ниже | `{}` |
| `drivers.<claude\|codex>` | `bin` — бинарь, `env` — переменные окружения этапов этого драйвера, `${VAR}` в значениях раскрывается из окружения движка, как в `skillPaths`, но переменная, в значении которой хоть одна `${VAR}` не задана, в этап не передаётся (в `skillPaths` незаданная — ошибка); `levels` — лестница драйвера: ровно пять уровней глубины `{ "model", "effort" }`, этап на этом драйвере идёт моделью своего уровня | `bin` — `claude` / `codex`, `levels` — см. «Драйверы» |
| `tracker` | `{ "type": "youtrack", "issuePattern": "<регулярка>" }` — номер задачи ищется регуляркой в имени ветки, текст задачи идёт этапам. `{ "type": "none" }` — без трекера | `none` |
| `sharedBranches` | общие ветки, чьё содержимое уже прошло ревью: в изменения задачи оно не попадает | `[]` |
| `stages` | объект: ключ — имя этапа, значение — настройка встроенного или свой этап (ниже). Каждый встроенный этап в нём обязателен: у него задаются драйверы | обязателен |

Встроенные этапы идут всегда; запись в `stages` с `drivers` нужна каждому из них — без неё конфиг не читается:

| Этап | Скилл метода | Уровень по умолчанию | Файлы по умолчанию |
|---|---|---|---|
| `assess` | `assessing-review-scope` | 1 | — |
| `threads` | — | 1 | — |
| `logic` | `reviewing-business-logic` | `"assessed"` | все |
| `quality` | `reviewing-code-quality` | 2 | все |
| `comments` | — | 1 | все, разбираются добавленные комментарии |
| `tests` | — | 1 | `**/tests/**` |
| `dedupe` | — | 1 | — |
| `skeptic` | `refuting-review-findings` | `"assessed"` | — |

Задание встроенного этапа — его шаблон в движке, по-английски: `logic` разбирает, делает ли
реквест то, что просили в задаче, и что он ломает, и закрывает разбор сводкой; `quality` проходит
каждый файл по каталогу своего скилла; `comments` — добавленные комментарии и докблоки с кодом под
ними; `tests` — поймает ли каждый тестовый кейс дефект. Метод `comments` и `tests` задаёт проект
своими скиллами в `skills.always`. Свой этап идёт общим шаблоном, в который подставляется его
`task`, и тоже закрывает разбор сводкой.

Ключи этапа:

| Ключ | Что задаёт | Встроенный | Свой | По умолчанию |
|---|---|---|---|---|
| `task` | задача этапа: кто он, что проверить и где ставить находку — первый абзац задания | ошибка | обязателен | — |
| `drivers` | непустой список драйверов этапа, `claude` и/или `codex`, без повторов. На каждый драйвер идёт свой экземпляр этапа, уровень этапа берётся на лестнице каждого. У служебных `assess`, `threads`, `dedupe`, `skeptic` — ровно один драйвер | обязателен | обязателен | — |
| `skills` | `{ "always": [...], "onDemand": [...] }`, оба списка необязательны. `always` — задание велит загрузить скилл до начала работы; `onDemand` — скилл доступен этапу, но в задании не называется: claude и codex сами видят скиллы этапа с `description` из frontmatter и берут подходящие к реквесту. Встроенному этапу скиллы добавляются к его скиллам метода, убрать их нельзя. Один скилл в обоих списках — ошибка | да | да | `{}` |
| `level` | `"assessed"` — уровень от оценщика, или число 1–5. У `assess` и `threads` — только число: они идут до вердикта | да | да | встроенный — свой уровень, свой этап — `"assessed"` |
| `allow` | команды сверх общего `allow` — только этому этапу | да | да | `[]` |
| `prompt` | как общий `prompt`, только этому этапу; перекрывает общий по ключам | да | да | общий `prompt` |
| `paths` | маски файлов (`src/**`, `**/*.php`); этап разбирает только их и не поднимается без них. Маска с `!` исключает, как в `.gitignore`: файл подходит, если подходит хотя бы под одну маску без `!` и ни под одну с `!` (`["**/tests/**", "!tests/e2e/**"]`); без масок без `!` подходят все файлы | у `logic`, `quality`, `comments`, `tests` | да | см. таблицу встроенных, свой — все файлы |

Имя своего этапа — `[a-z][a-z0-9-]*`.

### Пример

```json
{
  "version": 1,
  "skillPaths": ["${AGENT_TOOLS}/plugins/review/skills", "skills"],
  "allow": ["rg", "nav def", "nav ref"],
  "prompt": {
    "protocol": "`nav` is up and its index is current: its answers need no checking.",
    "plan": "Present a plan before your first search: the questions this stage has to answer, and where each answer comes from — the diff, a file to open, `nav def` for a declaration or `nav ref` for its callers."
  },
  "tracker": { "type": "youtrack", "issuePattern": "\\bPROJ-\\d+\\b" },
  "sharedBranches": ["develop", "main"],
  "drivers": {
    "codex": {
      "levels": [
        { "model": "gpt-6.1-terra", "effort": "medium" },
        { "model": "gpt-6.1-terra", "effort": "high" },
        { "model": "gpt-6.1-sol", "effort": "medium" },
        { "model": "gpt-6.1-sol", "effort": "high" },
        { "model": "gpt-6.1-sol", "effort": "xhigh" }
      ]
    }
  },
  "stages": {
    "assess": { "drivers": ["claude"] },
    "threads": { "drivers": ["claude"] },
    "logic": {
      "drivers": ["claude", "codex"],
      "skills": { "always": ["project-knowledge"], "onDemand": ["developing-backend", "developing-frontend"] }
    },
    "quality": { "drivers": ["codex"], "level": 4 },
    "comments": { "drivers": ["claude"] },
    "tests": { "drivers": ["claude"], "skills": { "always": ["reviewing-tests"] }, "paths": ["**/tests/**", "!tests/e2e/**"] },
    "dedupe": { "drivers": ["claude"] },
    "skeptic": { "drivers": ["claude"] },
    "docs": {
      "task": "You review the documentation this merge request changed: does it still match the code.",
      "drivers": ["codex"],
      "paths": ["docs/**"],
      "level": 1
    }
  }
}
```

## Драйверы

Встроены два, интерфейс у них один: сборка команды, песочница только на чтение, доставка
скиллов, разбор потока в телеметрию и цену, уровень → модель × усилие.

| | `claude` | `codex` |
|---|---|---|
| запуск | `claude -p`, задание в stdin, `--output-format stream-json` | `codex exec --json`, задание в stdin; команды — `bash -c`, не login-шелл (`allow_login_shell = false` в `config.toml` этапа): профиль образа сбросил бы `PATH`, и `review` пропал бы |
| песочница | `--permission-mode dontAsk`, `--allowedTools` — чтение, `Skill`, команды харнесса этапа и `allow`; вызов харнесса длиннее 10 000 символов, которого Claude Code не разбирает, пропускает хук `PreToolUse`; запись, веб, агенты и MCP запрещены | `--sandbox read-only`; харнесс и `allow` — правилами `prefix_rule` |
| изоляция | приватный `CLAUDE_CONFIG_DIR` с копией `~/.claude/.credentials.json` (заданный снаружи `CLAUDE_CONFIG_DIR` берётся как есть), `--setting-sources project` | свои `HOME` и `CODEX_HOME` на этап с копией `auth.json` и своим `config.toml` |
| скиллы | ровно `always` и `onDemand` этапа — плагином этапа (`--plugin-dir`), имена `stage:<скилл>`; скиллы `.claude/skills` дерева выключены через `skillOverrides` | ровно `always` и `onDemand` этапа — в `$HOME/.agents/skills` этапа; встроенные скиллы codex и скиллы дерева (`.codex/skills` и `.agents/skills` от рабочего каталога до корня репозитория) выключены в `config.toml` этапа; `always` — упоминанием `$<скилл>`, оно подключает скилл целиком |
| общий пакет | системным промптом: `--append-system-prompt-file` | developer-сообщением поверх базового промпта: `developer_instructions` в `config.toml` этапа (аргументом `-c` пакет не пройдёт — один аргумент ограничен 128 КиБ) |
| цена | из потока | по ценам OpenAI API (Standard, промпт длиннее 272K дороже) и usage каждого запроса из журнала сессии в `CODEX_HOME` этапа; известны `gpt-6.1-sol` и `gpt-6.1-terra`, у остальных моделей `$?` |
| размер контекста | пик по `usage` запросов в потоке | пик по журналу сессии |
| сессия этапа | `projects/<каталог>/<id>.jsonl` из `CLAUDE_CONFIG_DIR` | `config.toml`, `rules/` и `sessions/` из `CODEX_HOME` этапа, `usage` каждого запроса — в `cost.json` |
| вход | `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` или креды в конфиге | `CODEX_API_KEY`, `OPENAI_API_KEY` или `$CODEX_HOME/auth.json` |

Лестницы по умолчанию (`drivers.<имя>.levels` заменяет лестницу своего драйвера целиком):

| Уровень | `claude` | `codex` |
|---|---|---|
| 1 | `claude-sonnet-5-5` / medium | `gpt-6.1-sol` / medium |
| 2 | `claude-sonnet-5-5` / high | `gpt-6.1-sol` / high |
| 3 | `claude-opus-5-5` / low | `gpt-6.1-sol` / xhigh |
| 4 | `claude-opus-5-5` / medium | `gpt-6.1-sol` / max |
| 5 | `claude-opus-5-5` / high | `gpt-6.1-sol` / ultra |

## Окружение и preflight

| Переменная | Когда нужна |
|---|---|
| `GITLAB_TOKEN` | `--mr` и `--publish gitlab` |
| `GITLAB_URL` | `--mr project!iid` (ссылка на MR целиком несёт адрес сама) |
| `YOUTRACK_URL`, `YOUTRACK_TOKEN` | `tracker.type: youtrack` |

`--preflight` проверяет только своё: git, бинарь и вход каждого драйвера из `drivers` этапов,
токен GitLab при GitLab-входе, токен трекера, наличие скиллов. Без флага та же
проверка идёт перед каждым прогоном, и пробел его останавливает. Исключение — трекер:
без его переменных прогон идёт без текста задачи, с предупреждением в логе и строкой в
`gaps` отчёта; в JSON preflight такой пробел помечен `"blocking": false`. `ok` — нет
пробелов, останавливающих прогон.

```json
{ "version": 2, "ok": false, "gaps": [
  { "id": "skills", "message": "скиллы не найдены в skillPaths (…): reviewing-tests" },
  { "id": "tracker", "message": "трекер youtrack: не заданы YOUTRACK_TOKEN — разбор идёт без текста задачи", "blocking": false }
] }
```

## Отчёт

Артефакты прогона — `.llamer/<дата>_<время>/` в корне репозитория (сам `.llamer/`
игнорируется git): `report.md`, журналы этапов, задания, промпты, сырые потоки этапов,
`task.diff`, `cost.json`, плагин скиллов прогона и `sessions/<этап>/` — журнал сессии каждого
этапа с вымаранными секретами, без кредов. По каждому этапу llamer в конце печатает в лог
и пишет в `report.md` команду, которой сессию этапа можно продолжить вопросом агенту
(«зачем ты прочитал X повторно?»): `CODEX_HOME` или `CLAUDE_CONFIG_DIR` — каталог сессии в
артефактах, модель — та же, вход — ссылкой на обычное место кредов пользователя:

```sh
ln -sf ~/.codex/auth.json …/sessions/logic-codex/auth.json && CODEX_HOME=…/sessions/logic-codex \
  codex exec resume --skip-git-repo-check -c 'model="gpt-6.1-sol"' -c 'model_reasoning_effort="high"' <id> '<вопрос>'
ln -sf ~/.claude/.credentials.json …/sessions/logic-claude/.credentials.json && CLAUDE_CONFIG_DIR=…/sessions/logic-claude \
  claude -p --resume <id> --model 'claude-sonnet-5-5' --effort 'high' '<вопрос>'
```

JSON в stdout:

```json
{
  "version": 2,
  "input": "local",
  "head": "<sha>",
  "ok": true,
  "base": "<sha>",
  "assessment": { "nature": "behavioral", "risk": "medium", "level": 2, "reason": "…" },
  "findings": [{
    "id": 1, "stage": "logic", "driver": "claude", "file": "src/Order.php", "line": 4, "lineEnd": 4, "deleted": false,
    "severity": "major", "severityReason": "…", "text": "…", "suggestion": null,
    "related": [{ "file": "src/Order.php", "line": 4, "lineEnd": 4 }], "trace": null
  }],
  "summaries": [{ "stage": "logic", "text": "…" }],
  "resolvedThreads": [{ "id": "<id треда>", "place": "src/Order.php:4", "reason": "…" }],
  "gaps": [],
  "cost": { "usd": 0.42, "usdKnown": true, "turns": 31, "tokens": 512000, "contextTokens": 90000, "durationMs": 240000 },
  "report": "/путь/.llamer/…/report.md",
  "artifacts": "/путь/.llamer/…"
}
```

`version` — версия формата, сейчас `2`; меняется, когда поле убирают, переименовывают или меняют смысл.
`input` — `gitlab`, `local` или `range`; `head` и `base` — голова разбора и база изменений
задачи.

`findings` — то, что дошло бы до реквеста: повторы уже сняты дедупликацией, опровергнутые
скептиком находки убраны. Поля находки:

| Поле | Что значит |
|---|---|
| `id` | номер находки в журнале прогона |
| `stage` | имя экземпляра этапа, который её записал: `logic` или, у этапа на нескольких драйверах, `logic·codex` |
| `driver` | драйвер, на котором шёл этот экземпляр |
| `file`, `line`, `lineEnd` | файл от корня репозитория и строки фрагмента, включительно |
| `deleted` | `true` — строки удалённые, номера из версии до изменений; иначе — из головы |
| `severity` | `minor`, `major` или `critical` (с учётом пересмотра скептиком) |
| `severityReason` | на чём стоит вес |
| `text` | что не так и как это решить |
| `suggestion` | полная замена фрагмента или `null` |
| `related` | куда смотрел этап: `{ file, line, lineEnd }`, строки могут быть `null` |
| `trace` | цепочка рассуждения или `null` |

`summaries` — выводы разбирающих этапов, `resolvedThreads` — снятые треды (только при
`--mr`): `id` треда, `place` — `файл:строка` или `null`, `reason` — что его сняло; `cost` — цена и токены прогона (`usdKnown: false` — часть этапов цену не
назвала, и `usd` — сумма известных).
`gaps` — недостача прогона: пробелы окружения, с которыми он всё же пошёл, сорванные и
прекращённые этапы, находки без вердикта скептика. Своих изменений нет — `findings` пуст,
`assessment` — `null`.

Срыв — `"ok": false`, `failure: { reason, detail, text }` и пустой `findings`: найденное до
срыва остаётся в журнале прогона в артефактах. `reason` — одно из:

| `reason` | Что случилось |
|---|---|
| `auth` | авторизация драйвера недействительна |
| `rate_limit` | исчерпан лимит подписки драйвера |
| `timeout` | этап не уложился в лимит времени и был остановлен |
| `died` | процесс этапа завершился, не отдав итог |
| `killed:<сигнал>` | процесс этапа убит сигналом, например `killed:SIGKILL` |
| `scope` | не удалось отделить изменения задачи от чужих |
| `other` | прочий сбой прогона |

`detail` — подробность или `null`, `text` — то же человеческим языком.
