# LLaMer

Агентное ревью изменений в git-репозитории. LLaMer прогоняет изменения через несколько
этапов ревью на Claude Code или Codex: бизнес-логика, качество кода, тесты, комментарии.
Затем он убирает повторы, отдаёт каждую находку на проверку отдельному этапу-скептику и
публикует результат тредами в merge request GitLab или печатает его в YAML.

LLaMer ничего не знает о конкретном проекте и сам ничего не скачивает. Какие ревизии
разбирать, текст задачи, скиллы этапов и разрешённые команды передаёт тот, кто его
запускает: CI или агент. Настройки проекта лежат в `.llamer.json`, личные — в
`.llamer.local.json`.

## Требования

- Node.js 24 или новее.
- git 2.38 или новее (нужен `git merge-tree --write-tree`).
- `claude` или `codex` с выполненным входом.

Репозиторий готовят заранее: нужна полная история коммитов (неглубокий клон дополняется
командой `git fetch --unshallow --filter=tree:0`), исключаемые ревизии и целевая ветка MR в
`origin`. Скиллы этапов и всё, что им нужно (навигация по коду, Docker), тоже готовит
запускающий.

## Установка

```bash
npm i -g github:hakastein/llamer
llamer --help
```

Скилл [`llamer`](skills/llamer/SKILL.md) объясняет агенту, как запустить ревью и прочитать
результат. Формат — [Agent Skills](https://agentskills.io), его понимают Claude Code, Codex,
OpenCode, Gemini CLI, Copilot и Cursor.

```bash
npx skills add hakastein/llamer -g -y
```

## Быстрый старт

```bash
# проверить окружение, не запуская ревью
llamer --base HEAD --head worktree --preflight

# незакоммиченные изменения
llamer --base HEAD --head worktree

# своя ветка относительно main, со сверкой с задачей
llamer --exclude origin/main --head HEAD --task task.md

# merge request с публикацией тредов
llamer --mr https://gitlab.example.com/group/project/-/merge_requests/123 --publish gitlab
```

Результат печатается в stdout и сохраняется вместе с отчётом `report.md` в
`.llamer/<дата>_<время>/`. Лог пишется в stderr.

## Использование

### Что разбирать

Нужен либо `--mr`, либо `--head` вместе ровно с одним из `--base` и `--exclude`.

| Флаг | Описание |
|---|---|
| `--head <ревизия\|worktree\|index>` | Что ревьюить: ревизия; `worktree` — рабочее дерево с незакоммиченными и неотслеживаемыми файлами; `index` — индекс (staged). Для `worktree` и `index` делается снимок коммитом поверх `HEAD` через временную копию индекса, индекс пользователя не меняется. |
| `--base <ревизия>` | Ревьюить дифф от этой ревизии до головы. |
| `--exclude <ревизия>` | Не ревьюить то, что достижимо из этой ревизии. Можно указать несколько раз. Не сочетается с `--base`. См. [Что попадает в ревью](#что-попадает-в-ревью). |
| `--mr <url\|project!iid>` | Merge request в GitLab. База и голова берутся из него, целевая ветка исключается как `origin/<целевая>` и должна быть в репозитории. Не сочетается с `--head` и `--base`; `--exclude` добавляется к целевой ветке. Для `project!iid` адрес GitLab берётся из `GITLAB_URL` или `CI_SERVER_URL`. |
| `--task <файл>` | Текст задачи. Все этапы ревью, кроме `quality`, сверяют с ним реализацию. |

### Вывод

| Флаг | Описание |
|---|---|
| без флага | YAML в stdout и в `result.yaml`, отчёт `report.md` в каталоге прогона. |
| `--publish gitlab` | Опубликовать в MR заметку о рисках, треды находок на строках, сводку и статус; закрыть треды, проблема которых снята. Stdout пуст. Только с `--mr`. |
| `--dry-run` | Ничего не публиковать, выдать результат и отчёт. Только с `--mr`. |
| `--since-last` | Разобрать только изменения после прошлого прогона LLaMer в этом MR. Только с `--mr`. |

### Прочие флаги

| Флаг | Описание |
|---|---|
| `--config <файл>` | Конфиг вместо `.llamer.json` в корне репозитория. `.llamer.local.json` ищется рядом с ним. |
| `--preflight` | Проверить окружение, напечатать найденные проблемы в YAML и выйти. |

### Повторный прогон по MR

`--publish gitlab` оставляет в MR заметку-статус с меткой `llamer-rev` — ревизией, которую
разобрал прогон. С `--since-last` LLaMer находит последнюю метку, чья ревизия есть в истории
головы MR, и отсеивает всё, что было до неё, так же, как код целевой ветки. Метки вне истории
(после force-push или rebase) пропускаются с записью в лог.

- Подходящей метки нет или она совпадает с базой MR — разбирается весь MR.
- Новых изменений после метки нет — этапы не запускаются. С `--publish gitlab` в MR ничего
  не пишется и статус прошлого прогона остаётся в силе; без него выходит результат без находок.
- Этап сорвался, остановился командой `stop` или находка не опубликовалась — статус
  публикуется без метки, и следующий `--since-last` считает от последней полной метки.

### Коды выхода

Stdout содержит только YAML: результат или, с `--preflight`, список проблем окружения.

| Код | Когда |
|---|---|
| `0` | Прогон дошёл до результата. |
| `1` | Ошибка аргументов, конфига, входа или проблема из preflight: прогон не начинался, stdout пуст, причина в stderr. Прогон сорвался (`ok: false`). В результате есть недостача (`gaps`). |
| `130`, `143` | Прогон прерван SIGINT или SIGTERM. |

При прерывании LLaMer останавливает этапы вместе с их процессами и удаляет временные файлы:
копии учётных данных и выложенную ревизию. Записанные артефакты остаются, результата нет.

## Как это работает

Прогон идёт фиксированными шагами:

1. **Оценка.** Этап `assess` определяет характер изменения, риск и глубину ревью — уровень
   от 1 до 5. Без его вердикта прогон останавливается. С `--mr` одновременно идёт этап
   `threads`: он сверяет открытые треды прошлых прогонов с текущим кодом и закрывает те,
   проблема которых снята.
2. **Ревью.** Параллельно идут встроенные этапы `logic`, `quality`, `comments`, `tests` и
   этапы проекта из конфига. Этап с `paths` запускается, только если в изменениях есть
   подходящие файлы.
3. **Дедупликация.** Этап `dedupe` помечает находки разных этапов об одном месте и одной
   причине. Помеченные дальше не идут.
4. **Скептик.** Этап `skeptic` подтверждает или опровергает каждую оставшуюся находку и
   пересматривает её важность в любую сторону.
5. **Публикация** в GitLab или в YAML и `report.md`.

Этап можно запустить на нескольких драйверах сразу. Тогда на каждый драйвер идёт отдельный
экземпляр с общим заданием; в логе, отчёте и журнале он называется `<этап>·<драйвер>`,
например `logic·codex`. Экземпляры не видят находок друг друга, повторы между ними убирает
дедупликация. Если экземпляр сорвался, а этап отработал на другом драйвере, прогон не
проваливается: сорванный экземпляр попадает в `notices`.

На шагах с несколькими этапами первым стартует один, остальные — когда модель начала ему
отвечать.
Общая часть задания (дифф и треды) у всех этапов совпадает побайтно и попадает в кэш промпта
один раз.

Рабочая копия не меняется. Ревизию, отличную от `HEAD`, LLaMer выкладывает во временный
`git worktree` и удаляет после прогона.

### Что попадает в ревью

С `--base` ревьюится дифф от базы до головы как есть.

С `--exclude` и `--mr` ревьюятся изменения задачи: то, что голова добавляет ко всем
исключённым ревизиям — целевой ветке MR и каждой `--exclude`. База — коммит, в котором слиты
все общие предки головы с каждой исключённой ревизией (`git merge-base --all`,
`git merge-tree`). Поэтому код, пришедший в ветку слиянием из общих веток, в ревью не
попадает, в том числе при перекрёстных слияниях. Файл с конфликтом между исключёнными
ревизиями берётся по диффу MR, а без `--mr` — по диффу от точки расхождения с первой
`--exclude`.

Треды ставятся на строки диффа MR. Находка на строке, которой в диффе MR нет, публикуется
заметкой без привязки к строке.

Если голова ничего не добавляет к базе, этапы не запускаются и выходит пустой результат
(с `--publish gitlab` — статус в MR). Если изменения задачи вычислить нельзя (у головы нет
общей истории с исключённой ревизией, клон неглубокий), ревью не выполняется.

### Как этапы записывают находки

Этапы не пишут в GitLab сами. В `PATH` каждого этапа LLaMer кладёт команду `review`. Она
проверяет каждую запись — находка ставится только на изменённую строку, предложенная правка
должна применяться — и ведёт журнал прогона. Публикует результат сам LLaMer.

Набор команд зависит от этапа, чужие команды отклоняются:

| Этап | Команды |
|---|---|
| этапы ревью | `finding`, `amend`, `batch`, `list`, `blame`, `summary`, `diff`, `stop` |
| `assess` | `assess`, `diff`, `stop` |
| `threads` | `resolve`, `thread`, `list`, `batch`, `blame`, `diff`, `stop` |
| `dedupe` | `dupe`, `list`, `batch`, `blame`, `diff`, `stop` |
| `skeptic` | `verdict`, `list`, `blame`, `batch`, `diff`, `stop` |

`review --help` печатает команды этапа со справкой, `review <команда> --help` — справку одной
команды. В задании этапа справки нет, только отсылка к `review --help`.

`review diff <путь>...` печатает изменения задачи по файлам с полным контекстом; без
аргументов — список изменённых файлов со статусом и числом строк. Переименование
показывается парой `rename from/to`. Так этап дочитывает то, что не поместилось в задание.
Если полный дифф не помещается, удалённые файлы в нём свёрнуты до заглушки с числом строк, и
контекст диффа подбирается уже по свёрнутому варианту; `review diff` по удалённому файлу
печатает его целиком.

Скиллы встроенных этапов поставляются с пакетом (`src/skills/`), остальные берутся из
`skillPaths` конфига.

### Окружение этапов и секреты

Токен GitLab и текст задачи читает LLaMer, а не этапы. Окружение этапа собирается по белому
списку:

- `PATH`, `HOME`, `LANG`, `LC_*`, `TZ`, `TMPDIR`, `USER`, `SHELL`, `TERM`;
- `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY` в обоих регистрах;
- `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`;
- переменные входа своего драйвера (см. [Драйверы](#драйверы));
- служебные переменные `review` и `drivers.<имя>.env` из конфига.

Остальное, включая токен GitLab и `CI_*`, в этап не попадает. То, что нужно драйверу
(например адрес API), задаётся в `drivers.<имя>.env`.

Значения секретов, которые есть у LLaMer (переменные `*_TOKEN`, `*_KEY`, `*_SECRET`,
`*_PASSWORD`), вымарываются из публикаций в GitLab, `report.md`, YAML-результата, журналов
этапов и сессий и лога в stderr.

## Конфигурация

Конфиг проекта — `.llamer.json` в корне репозитория. Неизвестная версия или неизвестный
ключ на любом уровне останавливают прогон.

Конфиг и каталог `.claude/` проверяемого дерева исполняются как код: бинарь драйвера,
команды `allow`, настройки claude. LLaMer доверяет дереву так же, как CI, который его
запускает.

### Личные настройки

`.llamer.local.json` рядом с конфигом хранит настройки одного человека и в репозиторий не
коммитится. Он накладывается на конфиг по JSON Merge Patch (RFC 7396): объекты сливаются по
ключам, массивы и значения заменяются целиком, `null` удаляет ключ. Проверяется результат
наложения.

Все этапы на `claude`, `logic` дешевле:

```json
{ "driver": "claude", "stages": { "logic": { "drivers": null, "level": 2 } } }
```

`null` убирает у `logic` собственный список драйверов, и этап идёт на корневом `driver`.
Уровень `2` вместо `"assessed"` выбирает более дешёвую модель.

### Ключи конфига

| Ключ | Описание | По умолчанию |
|---|---|---|
| `version` | Версия схемы, сейчас `2`. | обязателен |
| `driver` | Драйвер всех этапов: `claude` или `codex`. Этап меняет его своим `drivers`. | обязателен |
| `skillPaths` | Каталоги скиллов; скилл — подкаталог с `SKILL.md`. Пути считаются от каталога конфига, `~` и `${VAR}` раскрываются, незаданная переменная — ошибка. Один скилл в двух каталогах — ошибка. Скилл с именем встроенного ошибкой не считается: этап получает встроенный. | `[]` |
| `allow` | Команды, разрешённые всем этапам: префиксы из слов без метасимволов оболочки (`"rg"`, `"git log"`). Команды `review` разрешены всегда. | `[]` |
| `prompt` | Строки задания, известные проекту. `protocol` дописывается в раздел «How This Run Works» после строк о поиске, `plan` заменяет план по умолчанию в разделе «Your Plan». Так проект сообщает этапам о навигации по коду, которую он поднял и разрешил в `allow`. | `{}` |
| `drivers.<имя>.bin` | Бинарь драйвера. | `claude`, `codex` |
| `drivers.<имя>.env` | Переменные окружения этапов этого драйвера. `${VAR}` в значениях раскрывается из окружения LLaMer; переменная, в значении которой есть незаданная `${VAR}`, в этап не передаётся. | `{}` |
| `drivers.<имя>.levels` | Лестница драйвера: ровно пять уровней `{ "model", "effort" }`. Этап идёт моделью своего уровня. | см. [Драйверы](#драйверы) |
| `stages` | Этапы: ключ — имя, значение — настройка встроенного этапа или свой этап. | `{}` |

### Встроенные этапы

Встроенные этапы идут всегда. Запись в `stages` нужна, только чтобы их настроить.

| Этап | Скилл метода | Уровень | Файлы |
|---|---|---|---|
| `assess` | `assessing-review-scope` | 1 | — |
| `threads` | — | 1 | — |
| `logic` | `reviewing-business-logic` | `"assessed"` | все |
| `quality` | `reviewing-code-quality` | 2 | все |
| `comments` | — | 1 | все |
| `tests` | — | 1 | `**/tests/**` |
| `dedupe` | — | 1 | — |
| `skeptic` | `refuting-review-findings` | `"assessed"` | — |

Задания встроенных этапов зашиты в пакет и написаны по-английски:

- `logic` проверяет, делает ли изменение то, что просили в задаче, и что оно ломает, и
  заканчивает сводкой;
- `quality` проходит каждый файл по каталогу своего скилла;
- `comments` разбирает добавленные комментарии и докблоки вместе с кодом под ними.
  Комментарий определяется по синтаксису языка файла; в Markdown, тексте и данных
  комментариев нет;
- `tests` оценивает, поймает ли каждый тестовый кейс дефект.

Метод `comments` и `tests` проект задаёт своими скиллами в `skills.always`. Свой этап идёт по
общему шаблону, в который подставляется его `task`, и тоже заканчивает сводкой.

### Ключи этапа

Имя своего этапа — `[a-z][a-z0-9-]*`.

| Ключ | Описание | По умолчанию |
|---|---|---|
| `task` | Задача этапа: кто он, что проверить, куда ставить находку. Первый абзац задания. Обязателен для своего этапа, у встроенного — ошибка. | — |
| `drivers` | Список драйверов вместо корневого `driver`, без повторов. На каждый драйвер идёт свой экземпляр, уровень берётся на лестнице каждого. У `assess`, `threads`, `dedupe`, `skeptic` — ровно один драйвер. | `[driver]` |
| `skills` | `{ "always": [...], "onDemand": [...] }`. `always` задание велит загрузить до начала работы. `onDemand` доступны этапу, но в задании не названы: драйвер сам видит их `description` и берёт подходящие. У встроенного этапа добавляются к скиллам метода. Один скилл в обоих списках — ошибка. | `{}` |
| `level` | `"assessed"` — уровень от оценщика, или число 1–5. У `assess` и `threads` только число: они идут до вердикта. | встроенный — свой, свой этап — `"assessed"` |
| `allow` | Команды сверх общего `allow` только для этого этапа. | `[]` |
| `prompt` | Как общий `prompt`, только для этого этапа; перекрывает общий по ключам. | общий `prompt` |
| `paths` | Маски файлов (`src/**`, `**/*.php`): этап разбирает только их и без них не запускается. Маска с `!` исключает, как в `.gitignore`: файл подходит, если подходит хотя бы под одну маску без `!` и ни под одну с `!`. Без масок без `!` подходят все файлы. Встроенным этапам — только `logic`, `quality`, `comments`, `tests`. | см. [Встроенные этапы](#встроенные-этапы), свой — все файлы |

### Пример

```json
{
  "version": 2,
  "driver": "claude",
  "skillPaths": ["${AGENT_TOOLS}/plugins/review/skills", "skills"],
  "allow": ["rg", "nav def", "nav ref"],
  "prompt": {
    "protocol": "`nav` is up and its index is current: its answers need no checking.",
    "plan": "Present a plan before your first search: the questions this stage has to answer, and where each answer comes from — the diff, a file to open, `nav def` for a declaration or `nav ref` for its callers."
  },
  "drivers": {
    "codex": {
      "levels": [
        { "model": "gpt-6.1-terra", "effort": "medium" },
        { "model": "gpt-6.1-terra", "effort": "high" },
        { "model": "gpt-6.1-sol", "effort": "medium" },
        { "model": "gpt-6.1-sol", "effort": "high" },
        { "model": "gpt-6.1-sol", "effort": "xhigh" }
      ]
    }
  },
  "stages": {
    "logic": {
      "drivers": ["claude", "codex"],
      "skills": { "always": ["project-knowledge"], "onDemand": ["developing-backend", "developing-frontend"] }
    },
    "quality": { "drivers": ["codex"], "level": 4 },
    "tests": { "skills": { "always": ["reviewing-tests"] }, "paths": ["**/tests/**", "!tests/e2e/**"] },
    "docs": {
      "task": "You review the documentation this merge request changed: does it still match the code.",
      "drivers": ["codex"],
      "paths": ["docs/**"],
      "level": 1
    }
  }
}
```

## Драйверы

Драйверов два, `claude` и `codex`. Каждый собирает команду запуска, закрывает этап в
песочнице только на чтение, доставляет скиллы, разбирает поток в телеметрию и цену и
переводит уровень в модель и усилие.

| | `claude` | `codex` |
|---|---|---|
| Запуск | `claude -p`, задание в stdin, `--output-format stream-json` | `codex exec --json`, задание в stdin. Команды идут через `bash -c`, не login-шелл (`allow_login_shell = false`): профиль образа сбросил бы `PATH`, и `review` пропал бы |
| Песочница | `--permission-mode dontAsk`; `--allowedTools` — чтение, `Skill`, `review` и `allow`. Хук `PreToolUse` пропускает вызов `review` длиннее 10 000 символов, который Claude Code не разбирает, и цикл `for f in <пути>; do review diff "$f"; done` по литеральным путям. Запись, веб, агенты и MCP запрещены | `--sandbox read-only`; `review` и `allow` — правилами `prefix_rule` |
| Изоляция | Свой `CLAUDE_CONFIG_DIR` с копией `~/.claude/.credentials.json` (заданный снаружи `CLAUDE_CONFIG_DIR` берётся как есть), `--setting-sources project` | Свои `HOME` и `CODEX_HOME` на этап с копией `auth.json` и своим `config.toml` |
| Скиллы | Только `always` и `onDemand` этапа, плагином этапа (`--plugin-dir`), имена `stage:<скилл>`. Скиллы `.claude/skills` дерева выключены через `skillOverrides` | Только `always` и `onDemand` этапа, в `$HOME/.agents/skills` этапа. Встроенные скиллы codex и скиллы дерева (`.codex/skills`, `.agents/skills`) выключены в `config.toml`. `always` подключается упоминанием `$<скилл>` |
| Общая часть задания | Системный промпт: `--append-system-prompt-file` | Developer-сообщение: `developer_instructions` в `config.toml` (аргумент `-c` ограничен 128 КиБ) |
| Цена | Из потока | По ценам OpenAI API (Standard, промпт длиннее 272K дороже) и usage каждого запроса из журнала сессии. Известны `gpt-6.1-sol` и `gpt-6.1-terra`, у остальных моделей цена `$?` |
| Размер контекста | Пик `usage` запросов в потоке | Пик по журналу сессии |
| Лимиты подписки | Событие `rate_limit_event`, окна `unifiedWindows` | Запись `token_count` журнала сессии, поле `rate_limits` (в потоке `--json` их нет) |
| Сессия этапа | `projects/<каталог>/<id>.jsonl` в `CLAUDE_CONFIG_DIR` | `config.toml`, `rules/` и `sessions/` в `CODEX_HOME` этапа; usage запросов — в `cost.json` |
| Вход | `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` или учётные данные в конфиге | `CODEX_API_KEY`, `OPENAI_API_KEY` или `$CODEX_HOME/auth.json` |

Лестницы по умолчанию. `drivers.<имя>.levels` заменяет лестницу целиком.

| Уровень | `claude` | `codex` |
|---|---|---|
| 1 | `claude-sonnet-5-5` / medium | `gpt-6.1-sol` / medium |
| 2 | `claude-sonnet-5-5` / high | `gpt-6.1-sol` / high |
| 3 | `claude-opus-5-5` / low | `gpt-6.1-sol` / xhigh |
| 4 | `claude-opus-5-5` / medium | `gpt-6.1-sol` / max |
| 5 | `claude-opus-5-5` / high | `gpt-6.1-sol` / ultra |

## Окружение и preflight

| Переменная | Когда нужна |
|---|---|
| `GITLAB_TOKEN` | `--mr` и `--publish gitlab` |
| `GITLAB_URL` | `--mr project!iid`; ссылка на MR целиком содержит адрес сама |

`--preflight` проверяет git, конфиг, бинарь и вход каждого драйвера, токен GitLab при `--mr`
и наличие скиллов. Без флага та же проверка идёт перед каждым прогоном, и любая проблема его
останавливает.

```yaml
version: 3
ok: false
gaps:
  - id: skills
    message: "скиллы не найдены в skillPaths (…): reviewing-tests"
```

## Результат

Артефакты прогона лежат в `.llamer/<дата>_<время>/` в корне репозитория, каталог `.llamer/`
игнорируется git. Там `result.yaml`, `report.md`, журналы этапов, задания и промпты, сырые
потоки этапов, `task.diff`, `cost.json`, плагин скиллов прогона и `sessions/<этап>/` —
журналы сессий этапов без учётных данных и с вымаранными секретами.

В stdout печатается тот же YAML, что в `result.yaml`; многострочный текст — блоками `|`.
`report.md` содержит то же для человека: заметку о рисках, находки, закрытые треды, сводку,
недостачу, команды продолжения сессий и таблицу цены.

```yaml
version: 3
input: revisions
head: <sha>
ok: true
base: <sha>
assessment: { nature: behavioral, risk: medium, level: 2, reason: … }
findings:
  - id: 1
    stage: logic
    driver: claude
    file: src/Order.php
    line: 4
    lineEnd: 4
    deleted: false
    severity: major
    severityReason: …
    text: |-
      Что не так.
      Как это решить.
    suggestion: null
    related: [{ file: src/Order.php, line: 4, lineEnd: 4 }]
    trace: null
summaries: [{ stage: logic, text: … }]
resolvedThreads: [{ id: <id треда>, place: src/Order.php:4, reason: … }]
gaps: []
notices: []
cost: { usd: 0.42, usdKnown: true, turns: 31, tokens: 512000, contextTokens: 90000, durationMs: 240000 }
limits:
  claude:
    status: allowed
    reason: null
    windows:
      five_hour: { usedPercent: 45, resetsAt: 1794480600 }
      seven_day: { usedPercent: 58, resetsAt: 1794787200 }
  codex: { status: rejected, reason: workspace_member_credits_depleted, windows: {} }
stages:
  - name: logic
    model: claude-sonnet-5-5
    effort: high
    ok: true
    usd: 0.21
    resume: CLAUDE_CONFIG_DIR=… claude -p --resume <id> --model … --effort …
report: /путь/.llamer/…/report.md
result: /путь/.llamer/…/result.yaml
artifacts: /путь/.llamer/…
```

| Поле | Описание |
|---|---|
| `version` | Версия формата, сейчас `3`. Меняется, когда поле убирают, переименовывают или меняют его смысл. |
| `input` | `gitlab` (`--mr`) или `revisions`. |
| `head` | Голова разбора; у `worktree` и `index` — коммит снимка. |
| `base` | База изменений задачи. |
| `ok` | `false` — прогон сорвался, см. [Срыв прогона](#срыв-прогона). |
| `assessment` | Вердикт оценки: `nature`, `risk`, `level`, `reason`. |
| `findings` | Находки, которые дошли бы до MR: без повторов и без опровергнутых скептиком. |
| `summaries` | Выводы этапов ревью. |
| `resolvedThreads` | Закрытые треды, только с `--mr`: `id`, `place` (`файл:строка` или `null`), `reason`. |
| `gaps` | Недостача: сорванные и остановленные этапы, находки без вердикта скептика. Непустой список даёт код 1. |
| `notices` | Сорванные экземпляры этапов, которые отработали на другом драйвере. Прогон не проваливают. |
| `cost` | Цена и токены прогона. `usdKnown: false` — часть этапов цену не сообщила, `usd` — сумма известных. |
| `limits` | Лимиты подписки по драйверам, см. [Лимиты подписки](#лимиты-подписки). |
| `stages` | Этапы прогона: модель, усилие, успех, цена и команда `resume`. |
| `report`, `result`, `artifacts` | Пути к отчёту, результату и каталогу прогона. |

Если разбирать нечего, `findings` и `stages` пусты, `assessment` — `null`, `cost` нулевой.

### Находка

| Поле | Описание |
|---|---|
| `id` | Номер находки в журнале прогона. |
| `stage` | Экземпляр этапа, который её записал: `logic` или, у этапа на нескольких драйверах, `logic·codex`. |
| `driver` | Драйвер этого экземпляра. |
| `file`, `line`, `lineEnd` | Файл от корня репозитория и строки фрагмента включительно. |
| `deleted` | `true` — удалённые строки, номера из версии до изменений; иначе строки из головы. |
| `severity` | `minor`, `major` или `critical` с учётом пересмотра скептиком. |
| `severityReason` | Чем обоснована важность. |
| `text` | Что не так и как это исправить. |
| `suggestion` | Полная замена фрагмента или `null`. |
| `related` | Куда смотрел этап: `{ file, line, lineEnd }`, строки могут быть `null`. |
| `trace` | Цепочка рассуждений или `null`. |

### Лимиты подписки

`limits` — последние сведения каждого драйвера о лимитах подписки за прогон: у claude из
события потока, у codex из журнала сессии. Драйвера, который сведений не прислал, в списке нет.

| Поле | Описание |
|---|---|
| `status` | `allowed`, `allowed_warning` (лимит на исходе) или `rejected` (исчерпан). |
| `reason` | Причина отказа словами драйвера (`credits_required`, `workspace_member_credits_depleted`, …) или `null`. |
| `windows` | Окна лимита: `five_hour`, `seven_day`; у codex окно другой длины называется `<минуты>_minutes`. `usedPercent` — использовано в процентах, `resetsAt` — время сброса в unix-секундах. |

Те же сведения LLaMer пишет в лог под таблицей цены:

```text
лимиты claude: 5 часов — использовано 45%, осталось 55%, сброс 2026-11-12 10:50 UTC; неделя — использовано 58%, осталось 42%, сброс 2026-11-16 00:00 UTC
лимиты codex: исчерпан (workspace_member_credits_depleted)
```

### Продолжение сессии этапа

`resume` в `stages` — команда, которой сессию этапа продолжают вопросом, например «зачем ты
прочитал X повторно?». Вопрос дописывается в конец в одинарных кавычках. `CODEX_HOME` или
`CLAUDE_CONFIG_DIR` указывает на каталог сессии в артефактах, модель та же, вход — ссылкой на
обычное место учётных данных пользователя. Те же команды есть в `report.md` и в логе:

```sh
ln -sf ~/.codex/auth.json …/sessions/logic-codex/auth.json && CODEX_HOME=…/sessions/logic-codex \
  codex exec resume --skip-git-repo-check -c 'model="gpt-6.1-sol"' -c 'model_reasoning_effort="high"' <id> '<вопрос>'
ln -sf ~/.claude/.credentials.json …/sessions/logic-claude/.credentials.json && CLAUDE_CONFIG_DIR=…/sessions/logic-claude \
  claude -p --resume <id> --model 'claude-sonnet-5-5' --effort 'high' '<вопрос>'
```

### Срыв прогона

Сорванный прогон отдаёт `ok: false`, `failure: { reason, detail, text }`, пустые `findings` и
`limits`. Найденное до срыва остаётся в журнале прогона в артефактах.

| `reason` | Что случилось |
|---|---|
| `auth` | Вход драйвера недействителен. |
| `rate_limit` | Исчерпан лимит подписки драйвера. |
| `timeout` | Этап не уложился в лимит времени и был остановлен. |
| `died` | Процесс этапа завершился, не отдав итог. |
| `killed:<сигнал>` | Процесс этапа убит сигналом, например `killed:SIGKILL`. |
| `scope` | Не удалось отделить изменения задачи от чужих. |
| `other` | Прочий сбой. |

`detail` — подробность или `null`, `text` — описание для человека.
